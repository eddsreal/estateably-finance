# Estateably Finance

Personal finance manager. Double-entry ledger, integer cents, single currency.
No application code exists yet; the stack is fixed by the constitution.

## Read before changing anything

- **[`.specify/memory/constitution.md`](.specify/memory/constitution.md)** — seven principles in
  priority order. It supersedes every other document here, including this one.
- Features follow the Spec Kit flow: `specify` → `plan` (contract frozen here) → `tasks` →
  `implement`. A feature's own spec, once it exists, is the second thing to read.

## The rules that break most often

The constitution is the authority; these are the ones that get code rejected.

1. Entries sum to zero, enforced in the domain _and_ by a database constraint, both inside one
   database transaction.
2. Money is an integer number of cents — `BIGINT` in the database, JSON strings of integer
   cents on the wire (`"4250"`, never a JSON number), `bigint`/`BigInt` arithmetic, never a
   float. Dollars exist only in the UI presentation layer.
3. `LedgerService.toEntries` is the only place intent becomes entries. The API and the UI never
   mention debits, credits or system accounts.
4. Modules talk through public services only — never another module's repositories, Prisma
   models or helpers.
5. Domain tests are not optional, even though `tasks-template.md` marks tests as
   "only if tests requested". Principle VI wins.

## How to work with me

**Spec Kit sets the order; I set the pace.**

- The numbered plan is `tasks.md`, generated by `/speckit.tasks`. Do not build a parallel list of
  phases outside the flow.
- The phases are the template's: Setup, Foundational, one per user story in priority order,
  Polish. Not one per module.
- `/speckit.implement` delivers **one phase and stops**, even though its own description says it
  processes every task in `tasks.md`. Wait for my approval before the next one. Never chain phases.
- The `review-spec` and `review-plan` gates are mine to approve. Never assume them approved.
- Implementation does not start before the plan's contract is frozen.

**Say when you are not sure.**

- If an environment variable is not in `.env.example`, ask before inventing it.
- For anything the spec does not cover: ask, or state the assumption in one line and keep going.

**Formatting.** Format every file you save with Prettier using this project's configuration. Do
not reformat files you did not touch.

**Comments.** Do not write comments of any kind in code or config files — no explanations, no
ceiling notes, no markers, nothing. Rationale, ceilings and upgrade paths are recorded in
`plan.md` (Complexity Tracking) or the feature's spec documents, never in the code.

**Git.**

- Commit only when I ask. Plain imperative subject line, optional body explaining _why_. I am the
  only author.
- Nothing about the assistant goes into the repository: no co-author trailers, no "generated
  with" footers, no mention of AI in commit messages, pull request descriptions or code comments.
